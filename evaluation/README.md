# Испытания качества 0.5.5

soar-0.5.5-draft.json — 30 черновых, ещё не запускаемых заданий шести классов. 18 разработочных, 12 контрольных, seed 17/53. Нет эталонных ответов, утверждения качества или зафиксированных пакетов источников. Факты исходного текста для правок сверены с source/current/products-editorial.json 01.11.2026; до испытаний требуется пакет той же версии.

Замораживание превращает черновик в evaluationSuiteSchema: каждому заданию необходимы digest пакета, digest проверенного эталона и сведения о проверившем. SHA-256 всего нормализованного набора связывает запуск с точной редакцией заданий, seed и участниками. Нельзя записывать выдуманные подтверждения или хеши вместо проверки эталона.

Разработочные задания используются для настройки. Контрольные ответы и результаты не включаются в подбор промптов, поиск, примеры голоса или обучение. evaluationInput отдаёт задание и ссылку на пакет, отвергает контроль в фазе разработки. Это граница модели данных, не файловая песочница или готовая интеграция исполнителя. Настройка на раскрытом контроле требует нового контрольного набора.

assessEvaluation принимает результаты одного фиксированного профиля. Все ожидаемые задания/seed остаются в знаменателе. Дополнительный удачный повтор не заменяет неудачу; он относится к новому эксперименту. Отмена/ошибка не считается формальным успехом. Человеческие оценки связаны с точными digest текста и эталона и двумя участниками. Слепое предъявление должен обеспечивать будущий интерфейс; флаг JSON сам по себе не доказывает слепую процедуру.

Приёмка: полный учёт попыток/оценок, 90% формальных контрактов, отсутствие неподтверждённых обещаний на контроле, принятие с малыми правками ≥80% контрольных попыток обоими участниками. Сопоставимость с эталоном считается отдельно. Unit-оценки синтетические и не являются пользовательской приёмкой.

Следующие шаги: закрепить источники/эталоны; исполнитель и измерения; профиль/голос; интерфейс оценки и очередь. Полный план: docs/V0.5.5_PLAN.md.

В ветке реализованы execution.ts (общий редакционный движок) и store.ts (сохранение попыток, контроль целостности и запрет замены повтором). Это нативный single-writer сервис, ещё не подключённый к пользовательскому диспетчеру. Контроль раскрывается только отдельной фазой; окончательная фиксация выбранного кандидата должна предшествовать этой фазе.

Для отдельной проверки работоспособности существует opt-in local-smoke.test.ts. Переменная WORKFLOW_EVALUATION_SMOKE_SOURCE указывает на sources.json ранее сохранённого снимка. По умолчанию используется первая разработочная задача knowledge-answer; WORKFLOW_EVALUATION_SMOKE_CASE выбирает точный ID другого разработочного задания. Контрольные задачи этим путём не запускаются. Исходный текст правки передаётся явно. Используются Mistral Small 3.2 24B, seed 17 и контекст 32768. Выход сохраняется под уникальным ID в ignored output/evaluation-0.5.5/development-smoke-*. Это не результат release evaluation, не доказательство качества или сравнимости с эталоном. Обычный npm test модель не вызывает.

Для нового снимка opt-in sources.test.ts принимает WORKFLOW_EVALUATION_SOURCE_CONFIG — путь к JSON с параметрами captureEvaluationSources. Новые результаты получают отдельный ID. В brief можно явно задать sourceIds обязательных записей: их отсутствие становится missing-source, а недостаточный бюджет не скрывается. Эти требования входят в хеш задания и проверку повторного построения пакета. Старые задания без sourceIds читаются без изменения их хешей.

WORKFLOW_EVALUATION_SMOKE_PROCESS позволяет передать точный снимок процесса, проверяемый verifyProcessSnapshot; его digest сохраняется в manifest, полная версия — в состоянии. Без переменной используется исходный процесс. Успешный smoke означает достижение awaiting-human, а не фактическую/языковую корректность: результат обязательно анализируется отдельно, ошибочный ответ не получает Human-подтверждение автоматически.

environment.jsonl содержит снимки среды на сохранении этапов: системная память, CPU, GPU и загруженные модели Ollama. unavailable/available=false означает неизвестное значение, не отсутствие нагрузки. Загруженная модель до старта позволяет отличить тёплый запуск от отсутствующей модели; это не доказывает совпадение prompt cache. Снимки не заменяют непрерывное профилирование. В summary дополнительно сохраняются объём и замечания каждой версии текста.

Внешний срок новых smoke-прогонов равен defaultEditorialBudget.timeoutMs (30 минут) и записывается как harnessTimeoutMs. Старые manifest без этого поля использовали 10 минут; отмена на этом сроке остаётся отменой, а не исправляется задним числом. Таймаут отдельного вызова по умолчанию — 300000 мс, либо значение проверенного process snapshot.

Нулевое число retrieval gaps означает только выполнение правил поиска, а не достаточность досье для эталонного ответа. При проверке статьи 01-gift обнаружено, что первоначальный пакет не содержит записей о запахе, технологии и упаковке, используемых принятым эталоном. Такой пакет нельзя считать равным контекстом для оценки качества бренда. Новый разработочный снимок фиксирует выбранные записи с их ограничениями, не меняя прежнюю попытку или утверждённую статью.

### Последовательный исполнитель серии

runner.ts выполняет выбранную фазу замороженного набора через EvaluationStore: все задания × все seed, один вызов за раз. До генерации проверяются все пакеты и текущий digest модели. Уже завершённые попытки, включая неудачи, читаются без повторного вызова. Отмена не создаёт фиктивные результаты для оставшихся заданий: expected сохраняет полный знаменатель. Начало каждой новой задачи получает собственный штатный срок; возобновление существующей не сбрасывает её deadline. Неопределённый pending обрабатывается общим движком как interrupted. Ошибка диска/контрольной точки останавливает серию, а не превращается в новую попытку. Выбор кандидата и открытие holdout остаются отдельным явным действием. Это нативный исполнитель, не пользовательский экран запуска эксперимента; реальная выпускная матрица ещё не выполнена.

### Запуск замороженной серии (opt-in)

`WORKFLOW_EVALUATION_SERIES_CONFIG` указывает на JSON с полями `sourcesPath`, `suitePath`, `referencesDirectory`, `phase` (`development` или `holdout`), `model`, `modelDigest` и необязательным `processPath`. Запуск: `npx vitest run src/evaluation/local-series.test.ts`. Отсутствие переменной пропускает тест без обращения к модели.

В каталоге эталонов необходим файл `<caseId>.json` для каждой задачи. До запуска проверяются полный состав, совпадение brief с источниками, packetDigest, текстовый SHA-256 и сведения редакторской сверки с suite. Эти тексты не передаются runner или provider. Данные серии сохраняются в `output/evaluation-0.5.5/series-<suiteId>/attempts`; каждый вызов стенда получает отдельный manifest/summary/environment.jsonl. Повтор того же конфига продолжает сохранённую серию, не заменяя прошлые результаты. Внешний срок — 24 часа, сроки отдельных редакционных задач не увеличиваются. Holdout требует предварительной фиксации кандидата через EvaluationStore; стенд её не выполняет автоматически. Зелёный результат стенда означает целостность выполнения, не прохождение порогов качества. Фактические ошибки и неполная серия видны в summary, человеческие оценки собираются отдельно.

Проверка всех файлов без модели: установите `WORKFLOW_EVALUATION_PREFLIGHT_ONLY=1` вместе с конфигом серии. Стенд проверит снимок, задания, эталоны и process snapshot и завершится до создания попыток/вызова Ollama. Этот результат означает только готовность входных данных; переменную нужно убрать для реального выполнения.

После контрольной фазы стенд формирует `series-<suiteId>/reviews` и `review-index.json` для двух участников. Повтор сохраняет расположение A/B и уже записанные оценки; ошибки/незавершённые/не начатые попытки остаются отдельными счётчиками. Это административная подготовка данных, не Human-подтверждение и не установка в рабочие профили.
