# ADR 0017: редакционные версии и отношения медиа

Дата: 25.10.2026. Статус: принято для реализации 0.5.4; не описание уже выпущенного поведения.

## Решение

Редакционная задача имеет валидируемый вход и последовательность неизменяемых версий. Planner, writer и reviewer получают собственный контекст. Исправление получает исходную задачу, тот же пакет источников, последний черновик и конкретные замечания; предыдущая ошибочная беседа не накапливается. Допускаются максимум два исправления после первого черновика, в одном общем бюджете. Истечение бюджета сохраняет уже полученные ответы.

Программная проверка отвечает за формальные свойства, наличие и разрешённость ссылок. Она не доказывает смысловую истинность. Отдельный reviewer сопоставляет утверждения и источники, а Human остаётся обязательным перед окончательным принятием текста. Ложноположительный вердикт reviewer не заменяет программные ограничения; отрицательный вердикт представлен человеку как замечание, не как установленный факт.

Подтверждение связано с ID задачи, ID версии и SHA256 точных UTF-8 байтов текста. Редактирование создаёт новую версию даже при сохранении исходного задания; одобрение прежней версии не переносится. История и checkpoints хранятся в runtime, ссылки и настройки — в domain. Следующий архитектурный шаг должен определить версию сериализованного проекта и миграцию до включения нового вида операции.

## Медиа

0.5.3 допускает только фото конкретного SKU. В 0.5.4 понятный каталог выбирает существующий точный код по названию/варианту, сохраняя устойчивые ссылки и проверки доступа. Не выводить идентичность товара из похожего названия или цвета и не подставлять фиктивные SKU для общих изображений.

Будущее расширение различает назначения product-evidence, style-reference и multi-product. Общий референс не подтверждает свойства товара; изображение нескольких товаров требует явного списка связей, а не одного случайного SKU. Введение этих назначений потребует новой схемы медиа/проекта, миграции старых фото в product-evidence и проверки контекста по назначению. В 0.5.4 новые назначения не исполняются; интерфейс честно объясняет ограничение и не теряет старые фото.

## Последствия

Обычные Agent не получают неявный редакционный цикл. Старые workflows продолжают исполняться по своим контрактам. Длительный редакционный процесс требует ограниченных бюджетов и отдельных checkpoints. Подтверждённая техническая готовность не означает художественную готовность 0.5.5.

## Формат проекта

Принято: project schemaVersion 0.6 добавляет необязательное operation.editorial к Agent. Это версия формата данных, а не приложения; выпуск приложения остаётся 0.5.4. Старые Agent не получают настройку автоматически. Схемы 0.5 заморожены отдельно, миграция 0.5 → 0.6 меняет только номер после резервного сохранения исходных байтов. Подмешивание editorial под прежним номером отклоняется.

Digest установленной модели читается через официальный [Ollama GET /api/tags](https://docs.ollama.com/api/tags), проверяется перед редакционным вызовом и сохраняется с параметрами. Прежние ModelProvider без identity продолжают работать для обычных Agent; редакционный путь требует явной идентификации модели.
