# Эволюция UX Workflow Architect

25.10.2026. Обзор выпущенной 0.5.3 по исходному коду, roadmap и обратной связи владельца. Это анализ и план, не новое пользовательское тестирование. Функции приложения этим изменением не меняются.

## Главный принцип владельца

«Как бы сложно не было технически устроено приложение — оно должно быть удобное, понятное, легкообучаемое, эстетичное, аккуратное, до такой степени, чтобы даже самый глупый человек смог бы разобраться в пользовании всем функционалом и предназначениями».

Рабочая формулировка: человек без технической подготовки понимает предназначение возможностей, находит задачу, получает результат и восстанавливается после ошибки. Инженерные функции остаются доступны и объясняются постепенно. Это проверяемая цель, не обещание мгновенного освоения любым человеком.

Фундамент можно строить до окончательного оформления. Но связи сущностей, права и порядок действий проверяются на задачах до закрепления архитектуры. UX — также поведение системы, а не только оформление.

## Где ещё не поздно

- До расширения медиа: различить фото товара, общий референс и изображение нескольких товаров. Не использовать выдуманный SKU. В 0.5.4 зафиксировать решение о связях, версиях и миграциях; новые виды медиа отдельно в 0.8.0.
- В 0.5.4: человек видит точную версию результата; «создано», «проверено», «одобрено» различаются.
- В 0.5.5: качество текста проверяется отдельно от удобства кнопок и формальной длины.
- До 0.6.0: понятны передаваемые данные, команды, изменение файлов и права Codex. Простой экран не означает скрытого согласия.
- В 0.6.1: режим ИИ отделён от сети; Telegram не выключается вместе с облачным ИИ.
- Canvas: постоянно проверять создание, соединение, Concept → Engineering, тест и публикацию; финальный сквозной контроль в 0.6.4. Непроверенные трудности навигации пока гипотезы, не установленные дефекты.
- До мультимедиа 0.8.0: спроектировать прогресс, отмену, стоимость, место на диске и восстановление.

## Приёмка каждой возможности

1. До кода описать задачу, исходное состояние, ожидаемый результат, необходимые знания, ошибки и восстановление.
2. Основной путь и расширенные параметры используют одну domain-модель и команды. Технические сведения доступны по запросу.
3. Проверить пустые данные, отсутствие сети/модели, ожидание, ошибку, отмену и повтор. Сообщение объясняет причину, сохранённую работу и следующий шаг.
4. Проверить композицию, читаемость, контраст, фокус, клавиатуру, масштаб и reduced motion. Справка работает без наведения мыши.
5. Раздельно записать технические результаты и наблюдение пользователя без подсказок разработчика. Не выдавать план за выполненную проверку.

Целевые метрики, пока не измеренные: каждый из двух пользователей самостоятельно проходит основной сценарий; для уже настроенного сценария от открытия до отправки задания — до трёх минут без времени генерации; находит результат, понимает статус, исправляет типовую ошибку. Первоначальное подключение измеряется отдельно с учётом внешнего сервиса. Нельзя улучшать метрику скрытием разрешений.

Для всего каталога возможностей проверяются назначение, обнаруживаемость, первый успешный шаг и восстановление. Редкие инженерные операции могут требовать встроенной инструкции. Обычный сценарий не должен требовать альманаха или чтения JSON.

0.5.4 снимает препятствия редакционной цепочки; 0.5.5 измеряет качество; новая 0.5.6 объединяет рабочее пространство. В 0.6.0–0.6.3 UX проверяется одновременно с инженерией. Новая 0.6.4 — контроль перед Beta, не начало UX. Декоративная полировка может ждать; непонятные права, потеря работы и блокировка основного пути — нет.

Дополнительные наблюдения по коду:

- `src/profiles/Setup.tsx` всё ещё обещает подключения «в следующих версиях». Это устаревшее описание существующей возможности. Исправить и проверить весь текст первой настройки в ближайшем выпуске, не ждать зрелой персонализации.

Это обзор исходников и предыдущей обратной связи, не повторная проверка установленного приложения и не новая приёмка владельцем.

## Полнота: проверяем весь жизненный цикл

Реестр в разделе 13 ROADMAP охватывает не только создание текста. Для каждой строки перед этапом составляется карточка: **задача человека → точка входа → минимальные действия → видимый результат → ошибка и восстановление → доказательство приёмки**. Реестр расширяется вместе с возможностями; функция без карточки не считается освоенной только потому, что у неё есть справка.

Для графа сохраняется исходная проверка §64 спецификации: создать, переименовать, соединить, переместить, открыть свойства, добавить узел и экспортировать без внешней инструкции. Затем проверяется более сложный путь Concept → Engineering → validation → публикация. Упрощение повседневных задач не убирает инженерный редактор.

## Когда UX нельзя откладывать

| Приоритет | Признак | Решение |
|---|---|---|
| Блокирует выпуск затронутой функции | Человек не понимает, что одобряет или куда отправляются данные; теряет работу; основной путь невозможно завершить | Исправить до приёмки вместе с техническим дефектом |
| Ближайший этап | Нужно копировать внутренний ID, читать JSON для обычной задачи, угадывать следующий шаг; интерфейс даёт ложное обещание | Назначить конкретный выпуск и повторить пользовательский сценарий; устаревшие обещания исправлять сразу в затронутом пути |
| Можно отложить | Декоративная доводка при уже понятном, доступном и аккуратном интерфейсе | Записать срок; контраст, фокус и читаемость не считать декором |

Зависимость задач важнее номера версии: выявленный блокер текущего пути нельзя переносить в 0.5.6 или 0.6.4 только потому, что там выделен UX-этап. Технический фундамент проверяется коротким работающим сценарием до расширения; визуальная полировка идёт по мере стабилизации взаимодействий.

## Как фиксировать приёмку

Для каждого пользователя отдельно записывать сборку, исходные условия, задание, результат, активное время без генерации, обращения к помощи, вмешательства разработчика и место затруднения. «Самостоятельно» означает отсутствие подсказок разработчика; встроенная помощь разрешена и её использование отмечается. Если разработчик подсказал, это диагностический проход; после исправления нужен новый самостоятельный проход.

Два основных пользователя дают приёмку для личного использования. Они не доказывают понятность для всех будущих пользователей open-source приложения. В Beta добавить, если доступен доброволец, проверку первого запуска человеком, не знакомым с проектом; при её отсутствии явно сохранить это ограничение.

Состояния карточки: **запланировано → реализовано в ветке → технически проверено → проверено пользователем → выпущено**. Исправленная кнопка не закрывает карточку до проверки всего пути. Установку, обновление и восстановление проверять на распространяемой сборке, а не только в браузерном стенде.

Связано: [Roadmap](ROADMAP.md), [правила агентов](../AGENTS.md), исходная спецификация §64. Выпущенная история сохраняется; долг закрывается будущими проверяемыми задачами.
