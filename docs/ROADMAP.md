# Workflow Architect — Roadmap до 1.0

Дата: 09.10.2026. Исходная версия: 0.2.0-alpha.1.

Статус: утверждён владельцем 09.10.2026. Начата разработка 0.2.0 по V0.2.0_PLAN.md. Это план будущей разработки, не перечень уже работающих функций и не обещание календарных сроков.

## 1. Цель Release 1.0

Open-source приложение для Windows 11, в котором два основных пользователя — владелец и его жена — могут без обязательного написания кода проектировать, запускать и проверять автоматизацию с ИИ-агентами, веб-сервисами, локальными инструментами и мультимедиа. Система поддерживает работу с актуальным Git-репозиторием, открытым в VS Code, встроенный цикл разработки и удалённые обращения через Telegram на постоянно включённом ПК.

Основной путь:

**Замысел → Concept → Engineering → проверка → реализация или настройка → тестовый запуск → действующий workflow → результат и история.**

Два связанных режима:

- **Автоматизация:** выполнение опубликованной, проверенной версии workflow через готовые узлы и интеграции. Генерация кода не требуется для каждого запуска.
- **Разработка:** coding-agent получает задачу, изменяет реализацию в отдельном рабочем каталоге, выполняет команды и тесты, представляет результат и diff, затем изменения принимаются в проект.

Окно редактора, выполнение workflow и coding-agent имеют разные жизненные циклы. Закрытие окна не должно прекращать разрешённые фоновые задачи. Выключение или сон ПК ограничивают доступность; после возвращения сервис восстанавливает сохранённое состояние и явно сообщает о прерванных действиях.

Спецификация v0.1 остаётся историческим источником требований к исходному редактору. Этот roadmap отражает явное расширение цели владельцем: runtime, реальные интеграции, credentials и исполнение команд планируются для следующих версий. Перед каждым таким этапом нужны его собственные требования, ADR и приёмочные сценарии. Общая цель не отменяет разделение UI, domain, commands, persistence и адаптеров.

## 3. Фундамент целевой архитектуры

| Подсистема | Ответственность |
| --- | --- |
| Desktop Editor | Canvas, Inspector, чат, настройка, наблюдение за выполнением и просмотр изменений |
| Domain и версии workflow | Устойчивая модель, схемы, ссылки, валидация; независимость от Canvas, LLM SDK и runtime |
| Execution compiler | Проверка исполнимости и преобразование инженерной модели в план выполнения |
| Local runtime service | Триггеры, планирование, задания, статусы, остановка и восстановление; работает отдельно от окна |
| Run store и artifacts | Журнал событий, результаты узлов, контрольные точки и ссылки на файлы; отдельно от описания графа |
| Model adapters | Вызовы моделей, capabilities, структурированный вывод, стоимость и ограничения |
| Integration adapters | HTTP, Telegram, MCP, файлы, выбранные веб-сервисы и мультимедийные провайдеры |
| Development runner | Coding-agent, изолированное выполнение команд, тесты, результаты и diff |
| Repository bridge | Привязка workflow к репозиторию, ревизии, worktrees, конфликты и связь с VS Code |
| Profiles, credentials, policies | Индивидуальные предпочтения, доступные подключения, лимиты и разрешения |

Запуск привязан к неизменяемой версии графа и конфигурации. Изменение Canvas во время выполнения создаёт черновик следующей версии. Результат запуска не перезаписывает описание workflow.

Следует отдельно определить версии формата проекта, протокола editor/runtime, execution plan и коннекторов. Для существующего формата 0.1 сначала создаются fixtures и миграции. Не предполагается, что нынешний IndexedDB станет единственной базой фонового сервиса: хранилище выбирается отдельным ADR, с проверяемым переносом старых данных.

## 4. Этапы до Beta

### 0.2.0 — Устойчивый редактор и основание open-source проекта

Результат: текущий редактор можно безопасно развивать, а пользователь проходит первую настройку перед основным рабочим пространством.

- Закрыть оставшиеся вопросы редактора: единые команды, scopes хоткеев, восстановление, квоты переносимых проектов и конфликт записи из нескольких окон.
- Добавить fixtures старых проектов, каркас миграций и резервную копию перед преобразованием формата.
- Ввести два именованных локальных профиля: предпочтения интерфейса, степень технической подробности, шаблоны и рекомендуемые лимиты.
- Первая настройка: цели, типовые задачи, опыт, предпочтение ручного/автоматического управления, доступные сервисы и короткая пробная задача. Можно пропустить, вернуться позже или настроить всё вручную.
- Пока без обязательного вызова ИИ: первый запуск не должен зависеть от ещё не настроенного ключа модели.
- Выбрать open-source лицензию до публикации, подготовить CONTRIBUTING, правила сообщений об ошибках и уязвимостях, сведения о сторонних компонентах. Подключить выбранный владельцем remote и реально запустить CI.

Приёмка: существующие проекты открываются; изменения и восстановление воспроизводимы; настройки двух профилей не смешиваются; опубликованный исходный код собирается по инструкции.

### 0.3.0 — Контракт выполнения и первый локальный runtime

Результат: инженерная схема действительно выполняется, отдельно от визуального Preview.

- Формализовать исполнение Flow/Data, Tool access, Reference, input/output contracts, Subworkflow, Human, условий и ограниченных циклов.
- Отделить «структурно корректный проект» от «исполнимого workflow»: неразрешённые Concept и неподдержанные операции не допускаются в запуск.
- Compiler строит execution plan; каждый запуск фиксирует версию плана и конфигурации.
- Первые исполняемые узлы: ручной Trigger, преобразование данных через формы, Logic, локальный Artifact, Human pause и Subworkflow.
- Статусы queued/running/waiting/succeeded/failed/cancelled, run ID, результаты узлов, события и явная отмена.
- Выбрать и проверить границу исполнения: UI не получает произвольный shell-доступ. Worktree отделяет изменения файлов, но сам по себе не является sandbox.

Приёмка: вручную собранный workflow с ветвлением и Subworkflow получает вход, выдаёт артефакт и объясняет ошибку на конкретном узле. Редактирование графа не меняет уже начатый запуск.

### 0.3.1 — Надёжное фоновое выполнение

Результат: runtime пригоден для всегда включённого домашнего ПК.

- Локальный фоновый сервис с аутентифицированным каналом связи с приложением; управление из tray, автозапуск по выбору пользователя.
- Сохраняемые задания, журнал, контрольные точки, лимиты параллельности и диска, timeout и отмена.
- Восстановление после перезапуска; пробуждение после сна; reconnect и понятное состояние недоступных подключений.
- Политики повторов, дедупликация входных событий и ключи идемпотентности там, где интеграция это поддерживает.
- Для внешнего действия с неизвестным результатом — reconciliation или запрос решения, а не слепой повтор. Универсальное exactly-once выполнение не обещается.
- Локальное хранение credentials вне графа и экспорта, маскирование в логах, отзыв разрешений. Привязки credentials принадлежат профилю.

Приёмка: закрытие окна не останавливает разрешённый run; перезапуск сохраняет историю и корректно классифицирует незавершённые действия; отменённая задача не продолжает незаметно выполнять инструменты.

### 0.4.0 — Работающие ИИ-агенты и помощник проектирования

Результат: Agent вызывает подключённую модель и использует разрешённые инструменты.

- Провайдерный интерфейс и первая реальная интеграция LLM; тест подключения и выбранных capabilities. Конкретные модели выбираются ближе к реализации, а не навсегда фиксируются roadmap.
- Роль, system prompt, structured output, контекст, ограниченный tool loop, память в заданных пределах и критерии завершения.
- Лимиты шагов, времени, токенов и расходов; остановка при превышении, видимая история вызовов.
- Несколько агентов в одном графе: последовательная передача и ограниченный параллелизм; корректное сведение результатов.
- Чат «опиши своими словами»: приложение уточняет замысел, предлагает граф и конфигурацию, показывает изменения, применяет их через editor commands с undo.
- После настройки модели — анализ ответов первого запуска и пробной задачи. Предложить 2–3 объяснимых набора настроек с возможностью ручного изменения и возврата к исходным.
- Поведение в отсутствие модели: ручной редактор и готовые не-ИИ workflow остаются доступны.

Приёмка: цепочка из двух агентов и одного инструмента даёт проверяемый результат, укладывается в лимиты; рекомендация ИИ не изменяет скрытно разрешения, credentials или настройки пользователя.

### 0.5.0 — No-code интеграции, MCP и Telegram

Результат: запускать и контролировать домашние процессы можно удалённо.

- Каталог коннекторов с формами, версиями, input/output schemas и тестом подключения.
- Базовый набор: HTTP/JSON, разрешённые локальные файлы, расписание, Telegram; один реальный веб-сервис из ваших задач. Авторизация реализуется по требованиям выбранного сервиса, без универсального OAuth-центра.
- Визуальное сопоставление полей между шагами, примеры payload, проверка входных/выходных данных; для типовой связки не нужно писать JavaScript.
- MCP client: подключение выбранных серверов, обнаружение инструментов и явные права. Инструмент MCP проходит ту же политику исполнения, что встроенный Tool.
- Telegram: текстовый входной Trigger, запуск разрешённого workflow, статус, остановка, уведомление, выдача файлов и Human approval.
- Telegram user/chat IDs привязаны к профилям; проверка отправителя, срока и принадлежности подтверждения конкретной операции.
- Изначально личные чаты и long polling: для домашнего ПК не нужен входящий публичный webhook. Сохранять update offset только вместе с надёжной регистрацией события и дедупликацией.
- Команда обычным языком сначала преобразуется в намерение и параметры разрешённого workflow. Открытый удалённый shell по произвольному сообщению не становится режимом по умолчанию.

Приёмка: оба пользователя запускают собственные процессы из Telegram, получают результат и не могут случайно использовать чужие подключения. Повторная доставка сообщения не создаёт незаметный повтор внешнего действия; обрыв сети и перезапуск имеют проверенный сценарий.

Техническая опора: Telegram Bot API предоставляет long polling через `getUpdates`; webhook и `getUpdates` не используются одновременно. Выбор polling здесь — проектное решение для домашнего deployment. [Telegram Bot API](https://core.telegram.org/bots/api#getupdates).

### 0.6.0 — Репозиторий, VS Code и полный цикл разработки

Результат: приложение получает задачу реализации, выполняет её и представляет проверяемые изменения актуального проекта.

- Подключение реальной папки Git-репозитория; branch, HEAD, dirty state, открытие в VS Code, отслеживание внешних изменений.
- В репозитории — версия workflow и manifest, связывающий stable node IDs с принадлежащими системе файлами, интерфейсами и тестами. Секреты, личные профили и run database не коммитятся.
- Coding-agent получает цель, контекст, разрешённые действия и критерии приёмки; работает в отдельной ветке/worktree через development runner.
- Встроенный цикл: план → изменение файлов → разрешённые команды → тесты/build → ограниченные исправления → отчёт, diff и артефакты.
- Просмотр вывода команд и тестов; различение успешного выполнения, ошибки, отмены и частичного результата. Лимит времени, расходов и числа итераций.
- Перед применением проверяется ревизия основы; внешние и несохранённые изменения не затираются. Конфликт вызывает review, а не автоматическое решение в пользу агента.
- Принятие изменений и отдельный Git commit; отмена правок графа и откат изменений репозитория — разные операции. Уже совершённые внешние действия не обещают универсального undo.
- VS Code bridge/небольшое расширение для состояния редактора, unsaved buffers, перехода от узла к коду/тесту и обратно.
- Изменения знакомых manifest-managed файлов можно сверять с графом. Произвольный код не считается автоматически и без потерь преобразуемым в Canvas; неподдержанное изменение становится расхождением для review.

Приёмка: задача на небольшую реальную функцию создаёт код, проходит согласованные тесты, показывает diff, применяется к актуальной базе и может быть отменена без потери пользовательских правок. Тесты запускаются в проверенной среде, а не с неограниченными правами процесса редактора.

Основной кандидат для глубокой интеграции — Codex app-server через отдельный адаптер: он рассчитан на встроенные приложения с сессиями, потоковыми событиями, прерыванием и обработкой запросов разрешения. Выбор API и режим авторизации фиксируются в ADR после прототипа на Windows. [OpenAI: Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform), [Codex App Server](https://learn.chatgpt.com/docs/app-server).

VS Code bridge должен учитывать Workspace Trust; само доверие workspace не заменяет изоляцию исполнителя. [Workspace Trust Extension Guide](https://code.visualstudio.com/api/extension-guides/workspace-trust).

### 0.6.1 — Сквозная сборка перед Beta

Результат: подсистемы работают вместе в пользовательском процессе.

- Одно представление задачи: замысел, версия workflow, run, coding session, commit и результат.
- Чёткие действия «Проверить», «Тестовый запуск», «Опубликовать версию», «Запустить», «Остановить», «Применить изменения».
- Telegram может инициировать ограниченную задачу разработки, показать состояние и запросить принятие результата. Сложный diff доступен в desktop, а не скрыт за одной общей кнопкой согласия.
- Личная подборка шаблонов каждому пользователю; контекстные подсказки и исправление обнаруженных UX-препятствий.
- Полная проверка сценариев с ошибками модели, внешнего сервиса, команды, диска и репозитория.

Приёмка: нет «демонстрационных заглушек» на обязательном пути; каждый из двух пользователей самостоятельно выполняет свой сценарий по интерфейсу и справке.

## 5. Beta — 0.7.0-beta.1

Beta — начало реальной ежедневной работы при управляемых ограничениях. К этому моменту уже доступны основные возможности, включая Telegram, LLM-агентов, Git/Codex и индивидуальные настройки.

Обязательные сквозные сценарии:

1. Текст в Telegram → агент → веб-инструмент → проверка ответа → документ → ответ в Telegram.
2. Задача реализации → актуальный репозиторий → worktree → код → тесты → diff → принятие результата.
3. Concept → предложенный Engineering → ручное уточнение → validation → тест → опубликованная версия workflow.
4. Персональные профили владельца и жены: разные предпочтения и подключения, предсказуемые права и уведомления.
5. Ошибка/отмена/обрыв связи/перезапуск → понятное состояние и восстановление без повреждения проекта.

Предлагаемые критерии входа:

- typecheck, lint, unit, integration, browser и desktop проверки проходят; core runtime тестируется также на управляемых mock-провайдерах;
- нет известных блокирующих дефектов потери данных, утечки credentials или обхода границ исполнения;
- каждый из первых трёх сценариев выполнен не менее пяти раз; оба пользователя самостоятельно завершили свою основную задачу;
- 72 часа фоновой работы с запланированными перезапуском и потерей сети; результаты восстановления задокументированы;
- старые проекты проходят миграцию и обратное восстановление из резервной копии;
- сохранены ориентиры Canvas 100/300 узлов; выполнение имеет отдельные измеренные лимиты.

Эти числа — приёмочные пороги плана, а не уже измеренные показатели продукта.

### 0.7.x-beta — Практика и устранение препятствий

- Собрать реальные неудобства отдельно у каждого пользователя.
- Исправить приоритетные дефекты и сократить повторяемые настройки.
- Улучшить диагностику, повтор запуска с изменёнными входами, просмотр данных между узлами и восстановление.
- Второй LLM-адаптер как проверка независимости архитектуры; локальная модель — при подходящем оборудовании и подтверждённых возможностях.
- Добавлять новые сервисы по реальным сценариям, а не по размеру каталога.

Критерий выхода: две недели регулярного использования обоими пользователями с сохранённым журналом проблем; нет нерешённых критических дефектов основных сценариев.

## 6. 0.8.0-beta — Мультимедиа и зрелая персонализация

Результат: платформа покрывает визуальные, видео-, аудио- и технические задачи, оставаясь понятной каждому пользователю.

- Изображения: анализ входного изображения и генерация/редактирование через выбранную интеграцию; preview и сохранение результата.
- Аудио: голосовой Telegram-ввод, транскрибация; озвучка при наличии выбранного провайдера.
- Видео: хотя бы одна согласованная сквозная цепочка создания или обработки короткого ролика. Сохранение внешнего job ID, polling, отмена, получение файла и прогресс длительной операции.
- Большие медиа хранятся как файлы/артефакты со ссылками, а не base64 внутри project JSON. Управление местом, сроками хранения и экспортом пакета.
- Технические инструменты: разрешённые CLI, обработка файлов и результатов сборки через общий execution broker.
- Индивидуальные рабочие пространства, избранные шаблоны, детализация интерфейса, модели, лимиты и стили уведомлений.
- Повторяемая диагностика предпочтений: ответы + короткие рабочие упражнения + объяснение рекомендуемых настроек. Это настройка рабочего процесса, а не психологическая оценка личности.
- Рекомендации ИИ имеют предпросмотр изменений и отмену; ручное управление доступно всегда. Автономность увеличивается только для явно выбранных классов действий.

Приёмка: одна полезная мультимедийная цепочка реально работает у каждого пользователя; хотя бы одна видеооперация выдерживает закрытие окна и восстановление состояния. Конкретные сервисы и квоты выбираются по доступным аккаунтам на этапе 0.5–0.8.

## 7. Pre-release — 0.9.0-pre.1

Результат: состав Release 1.0 зафиксирован. Новые типы возможностей откладываются до следующей версии.

- Закрытие известных значимых дефектов, проверка деградации при недоступных провайдерах и обновлении API.
- Backup/restore всей установки: проекты, manifest, настройки, история в выбранном объёме; перенос credentials выполняется отдельным явным способом.
- Проверяемый update/rollback приложения и runtime, совместимость протоколов, безопасное поведение при неподдерживаемой версии данных.
- Установка, обновление и удаление на чистой Windows 11; решение по подписи установщика и доверенному каналу получения обновлений.
- Документация пользователя, альманах, примеры, документация создания коннекторов и сборки из исходников.
- Проверка лицензии проекта, сторонних компонентов и включаемых ресурсов; публикационная готовность исходников.
- Проверка границ shell/MCP/HTTP, доступа к файлам, профилей, remote approvals и маскирования секретов. Произвольные внешние тексты не получают право менять политику исполнения.
- Настраиваемые лимиты истории и медиа, понятные показатели расхода моделей и места на диске.

Предлагаемые критерии входа/выхода: выполнены все обязательные сценарии 1.0; нет открытых P0/P1; не менее семи суток фоновой работы в тестовом цикле; восстановление после потери сети, остановки процесса и нехватки места проверено; performance и совместимость подтверждены для заявленных ограничений.

P0: потеря данных, утечка секретов, выполнение вне разрешённой границы. P1: основной сценарий не работает без приемлемого обхода.

Практики интеграции MCP проверяются по актуальной спецификации, включая разделение токенов и минимальные полномочия. [MCP Security Best Practices](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices).

### 1.0.0-rc.1 / rc.2 — Проверка кандидата

- Собрать версию из чистого checkout; проверить именно распространяемый установщик и обновление с предыдущей поддерживаемой версии.
- Повторить обязательные сценарии на отдельном профиле и реальных подключениях обоих пользователей.
- Исправлять только блокеры и существенные регрессии; каждое изменение повторно проходит затронутую приёмку.
- Финализировать release notes, известные ограничения, checksums и путь восстановления.
- После последнего значимого исправления — не менее семи дней приёмки кандидата без новых блокирующих дефектов. rc.2 выпускается при необходимости, количество кандидатов не фиксируется искусственно.

## 8. Release 1.0.0

Готовность означает, что владелец и жена могут самостоятельно настроить приложение, подключить свои сервисы и модель, создать или описать процесс, протестировать его, запустить с ПК или Telegram, получить результат, понять ошибку и восстановить работу.

В поставку входят исходники с выбранной лицензией, сборочная инструкция, Windows installer, документация, примеры, матрица поддерживаемых интеграций и протоколов, известные ограничения и порядок обновлений. Распространение исходников не означает предоставления бесплатного доступа к внешним моделям и сервисам: аккаунты и режимы доступа проверяются отдельно. OpenAI также разделяет открытый Codex harness и доступ к моделям/управляемым сервисам. [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform).

## 9. Правила синхронизации и индивидуальной работы

- Источник истины для структуры workflow — версионируемая domain-модель в проекте/репозитории; для файлов реализации — актуальные файлы Git-workspace; соответствие фиксирует manifest.
- Watcher обнаруживает изменение, но не принимает его безусловно. Изменение ревизии, dirty files и несохранённые буферы VS Code учитываются перед записью и запуском.
- Сгенерированные файлы имеют явные границы владения. Ручной код и пользовательские изменения не стираются ради восстановления предполагаемого соответствия Canvas.
- Личные настройки отделены от общих workflow; runtime фиксирует инициатора, профиль и разрешения запуска. Переключение профиля не должно менять уже идущие задачи.
- Профили внутри одного Windows-аккаунта не заявляются как ОС-изоляция друг от друга. При необходимости такой изоляции используются отдельные Windows-учётные записи и отдельно настроенные credentials.
- Настройка первого запуска допускает пропуск и повтор. ИИ-анализ включается после выбора работоспособного подключения; облачная отправка ответов видима пользователю.
- Оценка задачи ИИ, список шагов, разрешения и фактический результат показываются раздельно. Успех тестов не подменяется убедительным текстовым отчётом модели.

## 10. Зависимости и границы объёма

Порядок основного пути: **устойчивые данные → контракт выполнения → надёжный runtime → ИИ-агенты → интеграции/Telegram → репозиторий/Codex → сквозная Beta → мультимедиа/персонализация → Pre-release → RC → 1.0**.

Credentials, политика доступа и изоляция появляются до реального выполнения и удалённого управления. Миграции появляются до изменения формата. Профили и простая первая настройка — до ИИ-рекомендаций. Окончательная исполнимость инженерной модели — до произвольного наращивания каталога коннекторов.

До 1.0 не обязательны: облачная SaaS-платформа, биллинг, организация команд, marketplace, распределённые workers, мобильный Canvas, полная совместимость с n8n, подключение всех существующих веб-сервисов, универсальное восстановление графа из произвольного кода. Это не ограничивает нужные двум пользователям реальные локальные сценарии.

Постоянно действуют: строгая типизация, тесты контрактов и миграций, доступность, быстрый Canvas, согласованный визуальный стиль, проверки hover/focus/error/reduced motion, альманах для каждой новой возможности и небольшие проверяемые изменения.

## 11. Планирование следующего шага

Следующий этап — спецификация 0.2.0: редактор, переносимые данные, профили, первая настройка и open-source оформление. Параллельная по смыслу проектная работа — ADR контракта выполнения и репозитория; это не разрешение начинать все подсистемы одним изменением.

Перед каждым этапом фиксируются: пользовательские сценарии, точный объём, затронутые границы, формат данных, критерии приёмки и исключения. В конце — демонстрация, проверки и обновление фактического статуса roadmap.

Календарный прогноз строится после прототипов runtime и Codex на целевом Windows-ПК. Сейчас неизвестны выбранные сервисы, возможности оборудования для локальных моделей, длительность реального тестирования вдвоём и необходимость отдельных аккаунтов/устройств. Эти вопросы решаются в соответствующих этапах и не мешают утвердить порядок работ. Недели приёмки в Beta/Pre-release — реальное время наблюдения, которое нельзя заменить одним длинным сеансом разработки.
